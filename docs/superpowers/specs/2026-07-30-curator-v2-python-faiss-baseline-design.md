# Curator-v2 Python/FAISS Baseline Design

## Goal

Add a standalone Curator baseline runner that evaluates Curator-v2 on this
project's existing FilterVector datasets, query tasks, ground-truth files, and
result CSV conventions.

The baseline is intentionally external to the UNG C++ binary path. It should use
the Curator-v2 Python/FAISS implementation as the algorithm backend, while the
adapter code in this repository owns all data loading, containment-filter
translation, metric reporting, and output layout.

## Source Algorithm

Curator-v2 exposes `indexes/curator.py`, which wraps
`faiss.MultiTenantIndexIVFHierarchical`. The underlying idea is a shared
hierarchical IVF/clustering tree that can embed lightweight per-filter indexes
as subtrees. For predicate search, Curator-v2 supports explicit filter indexes,
bitmap filters, and optimized sorted internal-vector-id filters.

This project will treat Curator as a new FANNS baseline, not as a UNG route and
not as NaviX. NaviX is only a reference for how to package a standalone baseline
runner and keep output compatible with the current experiments.

## Scope

In scope:

- A Python runner under `experiments/curator_baseline/`.
- A repository-local adapter module that loads this project's `.bin` vector
  files and comma-separated label text files.
- Containment semantics: a base vector qualifies for a query iff its label set
  is a superset of the query label set.
- Integration with existing ground-truth format for recall computation.
- Per-`nprobe` or per-search-budget timing and recall summaries written in the
  same shape as existing `search_time_summary.csv` outputs.
- Config-driven execution over multiple datasets and query tasks.
- Index persistence under the existing result root, so repeated runs can reuse a
  built Curator index when the config matches.

Out of scope for the first implementation:

- Rewriting Curator-v2's FAISS extension in this repository.
- Adding a C++ `force_use_alg` route for Curator.
- Supporting non-L2 metrics unless the installed Curator-v2/FAISS backend already
  supports them through the same API.
- Building new ground-truth files from Python when the current C++ tool is
  unavailable. The runner may call existing C++ tools if configured, but the
  baseline itself assumes project-format GT exists or can be generated by the
  existing pipeline.

## Architecture

### Components

`experiments/curator_baseline/run_curator_baseline.py`

- Main entry point.
- Reads a JSON config modeled after `experiments/navix_baseline/config.json`.
- Resolves dataset paths, index paths, result paths, and search budgets.
- Ensures optional `.fvecs -> .bin` and GT generation through existing project
  binaries when enabled.
- Builds or loads the Curator index.
- Runs all configured query tasks and budgets.
- Writes result CSVs and logs.

`experiments/curator_baseline/curator_project_adapter.py`

- Loads project binary vectors: little-endian `uint32 num`, `uint32 dim`, then
  contiguous `float32` data.
- Loads label files: one vector per line, comma-separated integer labels, with
  empty lines treated as an empty label set.
- Loads query labels with the same parser.
- Loads project ground-truth binaries and exposes a `(nq, K)` integer matrix.
- Computes containment-qualified ids for each query label set.
- Computes recall against the project GT contract.

`experiments/curator_baseline/curator_backend.py`

- Imports Curator-v2's Python package from either `curator_repo` in config or an
  installed module path.
- Builds `Curator(d, ...)` and inserts all base vectors with external labels equal
  to project vector ids.
- Translates each query's containment-qualified ids into Curator bitmap or sorted
  vid filters.
- Executes `search_with_bitmap_filter` or the optimized sorted-vid path when the
  Curator-v2 backend exposes it.
- Returns project vector ids and distances/timing metadata.

### Data Flow

Build:

1. Read `base.bin` into a `float32` matrix.
2. Read `base_labels.txt` into `list[set[int]]`.
3. Instantiate Curator-v2 with config parameters such as `nlist`,
   `max_leaf_size`, `clus_niter`, `nprobe`, `prune_thres`, `search_ef`, and
   `beam_size`.
4. Train Curator on all base vectors.
5. Insert all base vectors with external ids equal to row ids.
6. Persist the Curator index and a local metadata file containing data hash,
   config, vector count, dimension, and label path hash.

Search:

1. Read query vectors and query labels.
2. For each query, compute the set of base ids whose base label set contains all
   query labels.
3. Pass that qualified-id set to Curator's bitmap-filter search API.
4. Pad missing results with `-1` so output shape is always `(nq, K)`.
5. Compute recall using the existing GT file.
6. Record total search time, average latency, QPS, recall, and optional Curator
   profile fields.

## Output Contract

The runner writes:

- `results/search_time_summary.csv`
- `results/search_time_summary_qps.csv`
- `results/curator_results_L<nprobe>.csv` or equivalent per-budget result files
- `others/<dataset>_curator_build.log`
- `others/<dataset>_curator_search.log`
- `index/Curator/index_files/curator_meta.json`

`search_time_summary.csv` should include at least:

- `Dataset`
- `Method`
- `K`
- `Lsearch` or `nprobe`
- `Recall`
- `Average_Time_ms`
- `Total_Time_ms`
- `Num_Queries`

The `QPS` column is added to `search_time_summary_qps.csv` with the same formula
used by the NaviX runner: `num_queries * 1000 / Average_Time_ms` when
`Average_Time_ms > 0`.

## Configuration

Add `experiments/curator_baseline/config.json` with fields:

- `curator_repo`: optional path to a checkout of `hatsu3/curator-v2`.
- `data_root`, `result_root`, `source_dir`, `build_dir`.
- `data_type`, `dist_fn`, `scenario`.
- `auto_compile`, `build_jobs`, and GT-generation controls matching the NaviX
  baseline runner.
- `build`: Curator construction parameters.
- `search`: `K`, repeats, thread count, and `nprobe_start/end/step`.
- `datasets`: dataset/query-task entries with path overrides matching existing
  experiment configs.

## Error Handling

- If Curator-v2 or its FAISS extension is unavailable, fail fast with a message
  explaining how to set `curator_repo` or install Curator-v2's FAISS Python
  package.
- If vector/label row counts mismatch, fail before building.
- If a query has no qualifying base vectors, return all `-1` and count recall as
  zero unless the GT row is also empty.
- If saved index metadata does not match the current dataset/config hash, rebuild
  rather than silently reusing a stale index.

## Testing

Unit tests:

- Vector `.bin` loader reads shape and dtype correctly.
- Label parser handles comma-separated labels and empty rows.
- Containment filter returns exactly the ids whose base label set is a superset
  of the query label set.
- Recall computation matches project GT rows and ignores padded `-1`.
- Config path resolution matches the NaviX baseline directory convention.

Integration smoke test:

- Build a tiny synthetic project-format dataset.
- Use a fake Curator backend when Curator-v2 is not installed.
- Run the Curator runner with one budget.
- Assert summary CSVs and padded result files are produced.

Manual verification:

- With Curator-v2 installed, run the smoke config against one real query task and
  compare output schema with NaviX/UNG summaries.

## Open Decisions

- The first implementation will use bitmap/sorted-id filtered search rather than
  building one Curator predicate index per unique query label set. This keeps the
  baseline practical for arbitrary project query tasks and preserves containment
  semantics exactly.
- `Lsearch` in project summaries maps to Curator `nprobe` for comparability in
  sweep scripts. CSVs should include both names when possible.
